PhishCard — разбор подозрительного сообщения

## Пользователь и боль
- Кто: Сотрудник поддержки / аналитик ИБ (SOC L1)
- Боль: <что делает сейчас, сколько времени, где ошибается — заполнить из кейса>

## Одна фраза решения
«<Пользователь> загружает <вход>, агент <действие> и возвращает <выход с доказательствами>, пользователь подтверждает, в результате <измеримый эффект>.» — заполнить после чтения кейса.

## Вход → выход
- Вход: Текст письма/сообщения, заголовки, URL как текст (без перехода)
- Выход: Признаки риска с основаниями, недостающие сведения, черновик карточки инцидента с приоритетом

## Шаги агента
1. Разобрать заголовки и ссылки (код)
2. Правила: несовпадение домена отправителя, punycode, сокращатели, срочность/деньги
3. Модель объясняет социальную инженерию
4. Аналитик подтверждает, экспорт карточки

## Что проверяет код (app/rules.py)
- From/Reply-To/Return-Path расходятся
- IDN/punycode и похожие домены
- сокращатели ссылок, IP вместо домена

## Проверка
- Набор: 20–40 сообщений (легитимные + фишинг, KZ/RU) с разметкой; precision/recall
- Бейзлайн: модель «это фишинг?» одним запросом

## Не заявлять
готовность к промышленной работе SOC; переходы по ссылкам и запуск вложений

## Запасные идеи трека
- Разбор логов входа: аномальные сессии с объяснением
- Проверка конфигурации (например, security headers сайта) с отчётом

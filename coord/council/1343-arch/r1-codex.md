**Слабости моего предложения:**

1. **План зависит от недоступного исполнителя.** Передача HTML Claude сейчас не обеспечена. В `app/` действительно только схемы, рейтинг и `__init__.py`; API, UI, LLM и хранение ещё предстоит реализовать. Обещание закрыть расширенную рубрику, деплой, постоянный диск и AI за первый час недостаточно обосновано.
2. **Слишком много инфраструктуры до сквозного сценария.** Отдельный `readers.py` для текстового ввода, расширенные источники, снимки, конкурентные изменения и два провайдера создают большой фронт работ. Без строгой очередности можно получить качественные компоненты без работающего отклика и выбора бизнеса.
3. **Проверка цитаты слабее заявленной защиты.** Источник «CRM нет» проходит проверку точного совпадения, даже если AI предлагает «CRM доступна». Человеческое подтверждение необходимо, но интерфейс должен показывать цитату рядом с конкретным утверждением. Само наличие evidence не означает отсутствие выдумок.
4. **Не определена атомарность подтверждения и публикации.** Между просмотром карточки и нажатием «Опубликовать» может завершиться AI-запрос или сохраниться правка. Проверка revision только при редактировании недостаточна: публикация должна проверять ту же версию и рассчитывать рейтинг на сервере.
5. **Есть неоднозначности продуктового контракта.** Три вопроса в каждом AI-ответе могут превратиться в бессмысленный опрос полностью заполненной карточки. «Максимальная прибавка» зависит от подтверждения и связанных полей. Не разграничены баллы готовности задачи и баллы прогресса команды; повторные этапы с произвольными названиями позволяют обходить UNIQUE.

## Обновлённое предложение

1. **Один процесс, минимальное разделение ответственности.** `schemas.py` — контракты; `rating.py` — начисления; `rules.py` — проверка источников; `llm.py` — провайдеры; `agent.py` — последовательность уточнения; небольшой модуль SQLite и API; одна HTML-страница. Для текстовых источников достаточно функции разбиения на абзацы, отдельный `readers.py` пока не нужен. Новые зависимости раскрываем в DISCLOSURE.

2. **Контракт карточки фиксируем до UI.** Сохраняем все обязательные поля кейса, включая название, тему, контакт и формат взаимодействия. Расширенную рубрику принимаем с весами 20/20/15/15/10/10/10 и ранее предложенными зависимостями подполей. Неизвестное — `null`, неподтверждённое — 0. Правка снимает подтверждение изменённого значения, связанные начисления пересчитываются. Одновременно обновляем тесты и synthetic-данные; две формулы не поддерживаем.

3. **AI предлагает, пользователь принимает.** Первый анализ задаёт минимум три различных уместных вопроса. Если пробелов мало, вопросы уточняют конкретность имеющихся сведений, не выдумывая недостатки. Последующие ответы обновляют предложение без обязательных трёх новых вопросов. Каждое заполненное AI-поле содержит источник, цитату и локатор; неверное доказательство блокирует перенос этого поля. Предложение не перезаписывает карточку автоматически. Рядом показываем источник, предлагаемое значение и действие подтверждения.

   Прибавку вычисляет `rating.py`: «до +N после заполнения и подтверждения», с указанием зависимостей. Прибавки разных вопросов нельзя механически суммировать.

4. **Публикация — одна транзакция.** Клиент передаёт ожидаемую revision. Сервер проверяет её, подтверждения и доказательства, рассчитывает балл и сохраняет опубликованный снимок. Устаревшая версия получает конфликт. Ручное подтверждение публикации отдельно от подтверждений полей: карточка с нулевым баллом допустима, пустое название — ошибка. Черновые изменения не затрагивают каталог до повторной публикации. Отклик сохраняет снимок условий, увиденных командой.

5. **Каталог и выбор без дополнительных барьеров.** Сортировка: рейтинг по убыванию, первая публикация и ID по возрастанию. Оба фильтра обязательны: тема и уровень. Показываем фактическое место в общем каталоге. Любая команда может откликнуться и на задачу с 0 баллов; поля предложения — идея, план, срок, ссылка. Бизнес выбирает ноль, одну или несколько команд, отклоняет остальные вручную. Выбор одной команды не закрывает другие отклики автоматически.

6. **Прогресс отделён от готовности.** Для MVP достаточно одного фиксированного этапа, например «результат этапа принят». Бизнес подтверждает его только выбранной команде. Начисляем учебные +10 команде, рейтинг задачи не меняем. Уникальное событие `(task_id, team_id, stage_id)` создаём транзакционно; повторный запрос возвращает прежний результат без повторного начисления. Свободное создание этапов исключаем.

7. **Отказы не останавливают ручной сценарий.** OpenAI — основной провайдер, NVIDIA — резерв с валидацией и одной попыткой исправления, затем явно обозначенная заглушка. Общий дедлайн ограничивает всю цепочку. Заглушка задаёт вопросы и оставляет неизвестные поля пустыми; пользователь продолжает вручную. Trace показывает фактического провайдера и режим каждого шага. В журнал не записываем ключи и полный текст контактов.

8. **Порядок реализации учитывает отсутствие Claude.** Codex планирует весь обязательный путь без зависимости от его возвращения. T-001/T-002 остаются людям. Первый контрольный результат — доступный URL с минимальным сервером и проверкой сохранения после перезапуска. Затем последовательно: конструктор и рейтинг → публикация и каталог → отклик и выбор → подтверждение этапа → интеграция и проверка отказов. AI подключаем к уже определённому контракту. Доступного позже Claude используем для независимого ревью, не блокируя разработку UI.

9. **Готовность доказываем сценариями.** Проверяем границы уровней и зависимости начислений; снятие подтверждений; публикацию низкого балла; оба фильтра; неизменность опубликованного снимка; конфликт revision; множественный выбор; повторное и конкурентное начисление прогресса; неверную цитату, отрицание, невалидный JSON и отказ API. Сохраняем минимум по пять черновиков, карточек, команд и откликов. Финальный проход выполняем через UI по URL, включая новый отклик и ручное решение.

При нехватке времени сокращаем оформление, дополнительные визуализации и сравнение откликов бок о бок. Обязательные переходы, оба фильтра, маркировку synthetic/mock, README и почасовые checkpoints не сокращаем. Независимое ревью пока считаем невыполненным; консенсус этого раунда не заявляем.

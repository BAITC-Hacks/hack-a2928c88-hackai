# Разработчик 2 — «Что изменилось после нашего отклика?»

## Зачем

Команда откликнулась на задачу с одним сроком и набором данных, а бизнес позже изменил условия. Покажите, на какие условия команда откликалась и что опубликовано сейчас. Это прозрачность сотрудничества, без автоматического выбора исполнителя.

Пример: «Было: прототип за две недели → Сейчас: за три дня». Эти строки берутся из реальных версий карточки, не генерируются AI.

## Границы и ветка

PR #3 уже слит. Начать новую ветку `team/catalog-conditions` от актуального `origin/main`, предварительно сохранив собственные незакоммиченные изменения. Не возвращать старую версию каталога.

Менять только `app/static/catalog.js`, `app/static/catalog.css`. Backend, api.js, бизнес-экран, рейтинг, приёмка этапа и хранение — часть капитана/Codex. Claude не вызывать.

Сохранить существующие поиск, серверную пагинацию, рекомендации, insights, черновики отклика, ручной выбор, +10 и `{refresh, focusCard}`.

## Что реализовать

1. В каждом отклике добавить раскрываемый блок **«Условия на момент отклика»**. Показать сохранённую версию, если известна. Без изменений блок компактный.
2. По явному действию пользователя получить актуальные **опубликованные** условия и сравнить с сохранённым снимком отклика. Показать изменившиеся поля: название поля / было / опубликовано сейчас.
3. Метка «Условия изменились после отклика» появляется только при реальной разнице текста. Разница номеров revision сама по себе не доказывает изменение условий: номер меняется и при подтверждении/публикации.
4. Пустое значение подписать «Не указано». Добавление и удаление текста тоже являются изменением. Сравнивать строки после нормализации CRLF → LF, не делать смысловое сравнение AI и не скрывать различия регистра/чисел.
5. Если тексты совпадают: «На момент проверки опубликованные условия совпадают с условиями отклика». Не писать «никогда не менялись»: промежуточной истории у нас нет.
6. Если снимка нет: «Условия на момент отклика не сохранены». Это ожидаемо для части синтетических примеров; не подставлять вместо истории текущую карточку.
7. При сетевой ошибке показать «Не удалось проверить актуальные условия» и повтор. Старый результат не выдавать за актуальный; не терять черновик отклика или решения.

## Действующий API: новый backend не нужен

`api.listProposals(cardId)` возвращает для новых откликов:

```js
{
  id, task_id, team_id, idea, plan, timeline, prototype_url,
  status, progress_points,
  card_revision, // версия опубликованной задачи при отправке
  task_snapshot // сохранённая опубликованная CardView
}
```

У старых/синтетических записей последние два поля могут отсутствовать. Проверять типы до чтения. `task_snapshot.id` должен совпадать с `proposal.task_id`; при несоответствии показать недоступность истории.

Актуальную опубликованную версию можно получить существующим `api.listCards({})` и найти по `id`. Для текущего объёма это допустимый временный вариант: **один запрос на явное обновление сравнения задачи, не отдельный запрос на каждый отклик**. Данные переиспользовать для всех откликов этой задачи. Обычная пагинация каталога остаётся серверной.

Не использовать `api.getCard(id)`: он возвращает рабочую карточку бизнеса, включая неопубликованные правки. Не полагаться исключительно на `state.selected`: карточка могла остаться со старой страницы. Если ID отсутствует в актуальном опубликованном списке — «Опубликованная версия недоступна», без вымышленного сравнения.

Показывать версию и время получения ответа как **время проверки**, а не дату редактирования. Защититься от позднего ответа: если пользователь открыл другую задачу, результат старого запроса не должен появиться в её панели.

Сравнивать только условия: `title`, `industry`, `context`, `need`, `users`, `data`, `constraints`, `expected_result`, `success_criteria`, `contact`, `interaction_format`, `feedback_process`. Использовать существующие русские подписи. Не включать служебные `rating`, `review`, `catalog_insights`, `confirmed_fields`, счётчики откликов или место в каталоге.

## Как показать пользу

В деталях задачи → «Отклики» → раскрыть историю нужного отклика:

- «Отклик на версию 4. Проверена опубликованная версия 7».
- «Изменено 2 поля».
- Таблица конкретных изменений.
- Подпись: «Изменение условий не означает согласие команды. Обсудите изменения перед началом работы».

Никаких фиктивных кнопок «Команда согласовала», нового статуса отклика или блокировки ручного решения. Согласование новых условий — отдельный будущий процесс.

## Приёмка на локальной учебной базе

1. Опубликовать задачу, отправить отклик: сравнение показывает совпадение условий.
2. Через API или экран бизнеса изменить данные/срок **без публикации**: сравнение в каталоге не показывает эти изменения.
3. Подтвердить и опубликовать изменения: у прежнего отклика ровно нужные поля в таблице, исходный снимок сохранён.
4. Отправить новый отклик после обновления: для него изменений нет. Каждый отклик сравнивается со своим снимком.
5. Повторно опубликовать тот же текст: revision изменился, предупреждения о текстовых изменениях нет.
6. Проверить добавление/удаление поля, старую запись без снимка, ошибку сети и переключение задач во время запроса.
7. HTML в тексте выводится буквально через `textContent`; новые ссылки не создаются из произвольной строки.
8. Отправка отклика, сравнение предложений, ручной выбор и однократные +10 продолжают работать. Нет ошибок консоли.

Для создания истории использовать только синтетические записи и локальный сервер, не публичную базу. Дополнительные тестовые файлы согласовать с ведущим, чтобы не пересечься с его тестами. Существующие smoke-скрипты не упрощать ради прохождения.
